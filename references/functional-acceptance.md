# 产品功能验收

仅在产品功能、PRD 或业务流程验收模式下读取。

## 验收依据

按以下优先级判断：用户在当前任务中的明确要求 > 指定 PRD / 验收标准 > 已确认业务规则 > 页面现状。若依据冲突，记录冲突并暂停受影响的结论，不自行选择有利于“通过”的解释。

## 建立用例

从需求中提取功能点、前置条件、角色、数据条件、触发动作、预期结果和禁止事项。围绕真实用户任务组织用例，而不是机械遍历所有按钮。

每个关键流程至少覆盖适用的：

- 正向流程：入口、输入、提交、处理中、成功和下一步。
- 逆向流程：取消、返回、关闭、退出、未保存提醒及上下文恢复。
- 异常流程：必填、非法值、边界值、重复提交、请求失败、超时、弱网、空数据、无结果、权限不足、登录过期、业务状态冲突。
- 状态与数据：Loading、Disabled、Error、Empty、Permission、Warning、Success；金额含币种，日期含必要格式或时区，敏感数据按权限脱敏。

不适用的状态标记 `N/A`，不要静默遗漏。

## Chrome DevTools MCP 执行

1. 使用 `new_page` / `navigate_page` 进入目标 URL，并用 `take_snapshot` 建立可访问结构基线。
2. 使用 `click`、`fill_form`、`press_key` 和 `wait_for` 执行交互；表单优先一次使用 `fill_form`。
3. 在开始一个测试动作前记录 Console 和 Network 基线；动作后只分析新增消息和关联请求。
4. 使用 `list_network_requests` 定位接口，用 `get_network_request` 核对方法、状态码和必要的已脱敏响应。不要在报告中暴露 Cookie、Authorization 或个人信息。
5. 使用 `take_screenshot` 保留初始状态、失败状态和必要的结果状态。成功流程一般无需为每一步截图，除非它证明关键验收点。
6. 需要弱网或离线验收时使用 `emulate`，完成后恢复网络和设备设置。

## 判定

- `通过`：实际结果与验收依据一致，关键状态已覆盖，没有相关 Console / Network 异常。
- `不通过`：有稳定复现步骤、明确依据和实际偏差。
- `待验证`：被账号权限、测试数据、环境故障或不可执行的高风险动作阻塞。

浏览器自动化策略或企业网络策略造成的阻断单独记录为环境阻塞，不作为网站产品缺陷。

## 缺陷描述要求

“问题描述（截图）/期望效果”单元格依次包含：

1. 前置条件。
2. 最短复现步骤。
3. 实际结果。
4. 对应 PRD / 验收条款。
5. 期望结果。
6. 问题截图。

“备注”放置 URL、账号角色、测试数据说明、接口方法/状态码、Console 摘要以及是否可稳定复现。
